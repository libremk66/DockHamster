# 通知模块改造 · 开发记录与总结（2026-10-09）

> 起因：用户要求"参考 MoviePilot 的通知把通知功能大改"，并明确**该模块可能复用到其它项目，必须可迁移、可复制**。
> 本文是开发记录 + 总结；**移植指南见 [`internal/notify/README.md`](../internal/notify/README.md)**（随包走，拷贝模块时一起带走）。

---

## 一、改造前的家底（起点）

- 渠道 7 个，**全部是 webhook 机器人**：飞书 / 企业微信 / 钉钉 / Bark / Server酱 / Telegram / 自定义 Webhook
- 配置是"一个渠道一个写死结构"，事件开关只有两个全局布尔（成功/失败）
- 纯文本消息、无模板、无历史、无降级

## 二、调研：MoviePilot v3 的通知长什么样

研究对象：`jxxghp/MoviePilot` **v3 分支**（与本机运行的 `moviepilot-v3` 对应）。相关源码位置：`app/modules/{feishu,wechat,qqbot,telegram,...}`、`app/schemas/notification.py`、`app/application/notification.py`。

提炼出的架构要点：

| 能力 | MP 的做法 | 本轮取舍 |
|---|---|---|
| 渠道模型 | 模块化（`capability.toml` 声明激活条件 / 配置出现且 enabled 才加载） | ✅ 抄"声明式注册"，不抄动态加载（Go 侧用静态注册表即可） |
| 能力表 | 每渠道声明 markdown/图片/按钮/长度上限 + **fallback 降级** | ✅ 抄"降级"（卡片→文本、markdown→文本） |
| 场景路由 | 9 类场景 × 每渠道订阅（`switchs`）+ 场景范围（all/user/admin） | ⏳ **规划中**（下一轮：场景开关） |
| 消息模板 | Jinja2 渲染标题/正文 | ⏳ 规划中（Go 侧将用 `text/template`） |
| 站内通知中心 | 消息持久化 + SSE 实时 + 清理水位（all/system/media） | ⏳ 规划中（下一轮） |
| 失败聚合 | 同媒体失败 30s 静默窗口合并一条 | ⏳ 规划中 |
| 聊天交互 | 按钮/回调/命令/语音（把 IM 当操作终端） | ❌ 不抄（与容器面板场景不匹配） |
| 多用户路由 | 渠道管理员、按 user 定向 | ❌ 不抄（本项目单管理员） |

## 三、本轮完成（时间线）

1. **飞书 → 支持自建应用**（`App ID + App Secret`，与 MP 同契约）
   - `tenant_access_token` 缓存（提前 10 分钟过期）→ `/open-apis/im/v1/messages`
   - 消息发**交互卡片**（标题按内容自动红/绿/蓝着色 + lark_md 正文），**失败自动回退纯文本**
   - 支持 Lark 国际版（可选域名）、接收者类型 open_id/user_id/email/chat_id（**email 最省事**）
   - 保留原群机器人 Webhook 模式，**二选一**（填了 App ID 走应用模式，老配置零改动）
2. **QQ → 官方机器人**（`AppID + ClientSecret`，MP 同款）
   - `getAppAccessToken`（提前 5 分钟刷新）→ `/v2/groups|/v2/users/.../messages`
   - Markdown（`msg_type=2`）优先、失败回退纯文本（`msg_type=0`）
   - ⚠️ 官方硬限制：**主动消息 4 条/月/群（或用户）且需先交互**——已写进表单提示与错误提示
3. **企业微信 → 支持应用消息**（`CorpID + Secret + AgentID`，MP 同款，可推个人微信）
   - `gettoken`（提前 5 分钟）→ `/cgi-bin/message/send`
   - 正文 **2048 字节按行分块逐条发送**（不切断多字节字符）；官方 errmsg 调试尾巴自动清洗
4. **模块抽包**：`internal/module/notify*.go` → **`internal/notify/`**（新包）
   - **零第三方依赖**（唯一用到的 uuid 换成本地随机 hex），拷贝即用
   - 配置 JSON 字段**完全不变** → 无需迁移；调用点 6 处改为 `notify.Send / notify.SendOne`
   - 配套单测随包迁移

## 四、验证记录（全部实测）

**逐渠道"假凭据真实调用"的报错样本**（证明链路通、错误可读）：

| 渠道 | 输入 | 面板实际返回 |
|---|---|---|
| 飞书应用 | 缺 Secret | `发送失败：未填 App Secret` |
| 飞书应用 | 假凭据 | `获取租户令牌失败：应用凭据无效或应用未启用（code=10014 app id not exists）` |
| QQ | 缺 Secret | `发送失败：未填 ClientSecret（机器人密钥）` |
| QQ | 假凭据 | `获取 AccessToken 失败：AppID/ClientSecret 无效（code=10004 机器人不存在）` |
| 企业微信 | 缺 Secret | `发送失败：未填应用 Secret` |
| 企业微信 | 假 CorpID | `获取 access_token 失败：CorpID 或应用 Secret 不正确（errcode=40013 invalid corpid）（请核对 CorpID 与应用 Secret）` |

**单测**：字段校验（不联网直接报错）、飞书卡片配色、JSON 取值帮助函数、QQ 错误码提示映射、企业微信分块（每块 ≤2048 字节）——全绿。

**部署验证**：均通过测试实例（`dockhamster-test:12888`，`dh-dev.sh` 构建）实测；前端表单截图核对。

## 五、关键决策记录

| 决策 | 理由 |
|---|---|
| 一个渠道支持两种模式（应用 / Webhook）二选一 | 不破坏老配置；用户手里有什么用什么 |
| token 只缓存在内存 | 进程级、生命周期短；落盘反而要处理加密与失效 |
| 错误信息必须"翻译 + 附操作提示" | 原始 errcode（如 40013 invalid corpid）对用户没有可操作性 |
| 富格式必须带回退 | 卡片/Markdown 在部分租户或未开通权限时不可用，回退保证"总有一条能到" |
| 抽包而非原地重构 | 用户要复用到其它项目：包内零依赖 + 自带 README，拷贝即可 |
| 不抄聊天交互与多用户路由 | 与"单向推送"的产品定位不符，复杂度不成比例 |

## 六、已知限制与后续规划

**限制**：
- QQ 主动消息配额（4 条/月/目标）——官方限制，无解，只能当兜底渠道
- 飞书卡片在部分企业租户不可用 → 已有纯文本回退
- 企微应用消息需成员关注"微信插件"才能进个人微信

**后续规划（按优先级）**：
1. **场景开关**：每个渠道订阅哪些事件（更新成功/失败/容器异常/面板自更新/发现新版本），替代现在"成功/失败"两个全局开关
2. **消息模板**：`text/template` 变量注入，每渠道可自定义文案
3. **站内通知中心**：消息落盘 + 面板「通知」页 + 实时刷新（对标 MP 的 Web/WebPush 渠道）
4. **聚合去抖**：容器异常按容器分组、批量失败合并（对标 MP 的 30s 窗口）
5. **更多渠道**：Gotify / ntfy / 邮件 SMTP / PushPlus / PushDeer

## 七、复用到其它项目怎么做
